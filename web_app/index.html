Hybrid Encryption: 12-Step Real-World File Transfer

Demonstrates how AES-256-GCM (symmetric encryption), RSA-2048 (asymmetric key encapsulation), and SHA-256 (integrity verification) collaborate in production protocols. Below, each of the 12 steps is shown individually with its exact action, security explanation, and cryptographic output.

Step 1: Receiver Generates RSA-2048 Key Pair

Participant: Receiver (Device A)
Ready
What is Happening:

The receiver's browser invokes window.crypto.subtle.generateKey to create a mathematically linked 2048-bit RSA key pair: a Public Key ($e=65537, N$) and a Private Key ($d, N$) configured with OAEP padding and SHA-256.

Why It Is Done (Security Rationale):

Asymmetric cryptography eliminates the need for a pre-shared secret. The public key can be given to anyone, but only the holder of the private key can decrypt messages intended for them.

Step 2: Receiver Shares Public Key with Sender

Participant: Receiver ➔ Sender
Waiting for Step 1
What is Happening:

The receiver exports the RSA Public Key into standard SubjectPublicKeyInfo (SPKI) PEM format and transmits it to the sender across the network (via TLS, email, or key registry).

Why It Is Done (Security Rationale):

Public keys are mathematically safe to distribute across untrusted or public networks. Intercepting a public key does not allow an eavesdropper to decrypt any ciphertext.

Step 3: Sender Selects Confidential File (PDF / Document)

Participant: Sender (Device B)
Ready
What is Happening:

The sender selects a file (such as a confidential PDF, image, or document). The browser reads the file's raw binary octets into memory as an ArrayBuffer.

Why It Is Done (Security Rationale):

Directly encrypting large files with RSA is computationally prohibitive and impossible beyond 190 bytes (RSA-2048 with OAEP-SHA256). Therefore, the raw file is buffered for high-speed symmetric AES encryption.

Why It Is Done (Security Rationale):

Generating a unique one-time session key for every single file transfer guarantees forward secrecy and prevents key-reuse vulnerabilities across different files.

Step 5: AES-256-GCM Encrypts the File Payload

Participant: Sender (Crypto Engine)
Waiting for Key
What is Happening:

The 256-bit AES key encrypts the full file binary data using Galois/Counter Mode (GCM). GCM simultaneously creates ciphertext and computes a 128-bit authentication tag.

Why It Is Done (Security Rationale):

AES-GCM is an Authenticated Encryption with Associated Data (AEAD) algorithm. It provides military-grade bulk confidentiality while guaranteeing ciphertext integrity against any modification.

Step 6: RSA Encrypts AES Key via Receiver's Public Key (Key Encapsulation)

Participant: Sender (Key Encapsulation)
Waiting for Step 4 & 2
What is Happening:

The small 32-byte raw AES key is encrypted using the Receiver's RSA-2048 Public Key with Optimal Asymmetric Encryption Padding (OAEP) and SHA-256.

Why It Is Done (Security Rationale):

This is Key Encapsulation. The heavy file is encrypted with fast AES, and only the tiny 32-byte AES key is encrypted with RSA. This gives asymmetric security with symmetric speed.

Step 7: SHA-256 Calculates Original File Digest

Participant: Sender (Integrity Hash)
Waiting for File
What is Happening:

The sender passes the unencrypted original file bytes through the SHA-256 cryptographic hash function to compute a fixed 256-bit (64 hexadecimal characters) digest.

Why It Is Done (Security Rationale):

Hashing creates an unforgeable digital fingerprint. Even if a single character of the file is changed, the Avalanche Effect will produce a completely different hash on the receiving end.

Step 8: Application Builds Encrypted JSON Transfer Package

Participant: Sender ➔ Network
Waiting for Steps 5, 6, 7
What is Happening:

The application bundles the RSA-encrypted AES key, the AES-GCM file ciphertext, the 12-byte IV, the original SHA-256 hash, and file metadata into a standardized .secpack.json package.

Why It Is Done (Security Rationale):

Bundling all cryptographic artifacts into a structured transfer envelope ensures interoperable, portable transmission across any network channel, email, or cloud storage.

Step 9: Receiver Recovers AES Key via Private Key

Participant: Receiver (Station C)
Waiting for Package
What is Happening:

The receiver extracts the 256-byte encrypted key from the package and uses their secret RSA Private Key ($d$) to decrypt it using RSA-OAEP with SHA-256.

Why It Is Done (Security Rationale):

Only the legitimate recipient possessing the secret private key can invert the modular exponentiation $m = c^d \pmod N$ to recover the 32-byte AES key. Eavesdroppers cannot decrypt it.

Why It Is Done (Security Rationale):

Fast hardware-accelerated symmetric decryption instantly reconstructs the original document (even large PDFs) while simultaneously validating the 128-bit authentication tag.

Provides mathematical proof of integrity. If the computed hash matches the original hash 100%, the receiver is guaranteed that the file was never modified, corrupted, or tampered with.

🔬 AES-256-CBC Internal Cryptographic Breakdown:

Step 1
Password Ingestion & Salt Generation (8 Bytes)

OpenSSL reads the user passphrase and generates an 8-byte random cryptographic salt using CSPRNG. In the output file encrypted.bin, OpenSSL writes the 8-byte magic header Salted__ followed immediately by this 8-byte salt.

File Header: 0x53616C7465645F5F (ASCII "Salted__") + 8 bytes Salt
Step 2
PBKDF2 Key & IV Derivation (100,000 Iterations)

OpenSSL executes Password-Based Key Derivation Function 2 (PBKDF2) using HMAC-SHA256 across 100,000 iterations. It derives a 256-bit (32 bytes) symmetric key $K$ and a 128-bit (16 bytes) Initialization Vector $IV$.

Formula: DK = PBKDF2(HMAC-SHA256, Password, Salt, c=100000, dkLen=48 bytes)
Step 3
PKCS#7 Plaintext Padding (128-bit / 16-byte Blocks)

AES operates strictly on fixed 16-byte blocks. If the message length is not an exact multiple of 16, PKCS#7 appends $N$ bytes, each with value $N$ (e.g., if 3 bytes are missing, it appends 0x03 0x03 0x03). If the message is already a multiple of 16, a full 16-byte padding block is added.

Block Size = 128 bits (16 bytes) | Padding bytes = 16 - (length mod 16)
Step 4
CBC Mode Chaining & XOR Operation

In Cipher Block Chaining (CBC) mode, each 16-byte plaintext block $P_i$ is XORed with the previous ciphertext block $C_{i-1}$ before entering the encryption cipher. For the first block ($P_1$), it is XORed with the derived Initialization Vector ($IV$).

Chaining Formula: C_i = AES_K( P_i ⊕ C_{i-1} ) with C_0 = IV
Step 5
The 14 Internal Rounds of AES-256 (Substitution-Permutation Network)

For a 256-bit key, AES executes exactly 14 transformation rounds on a $4 \times 4$ byte state matrix:

  • SubBytes: Non-linear byte substitution using the Rijndael S-Box lookup table based on multiplicative inverse in $GF(2^8)$.
  • ShiftRows: Permutation that cyclically shifts Row 0 by 0 bytes, Row 1 by 1 byte, Row 2 by 2 bytes, and Row 3 by 3 bytes.
  • MixColumns: Matrix multiplication in Galois Field $GF(2^8)$ providing inter-column diffusion (rounds 1–13; omitted in round 14).
  • AddRoundKey: Bitwise XOR of the state matrix with the 128-bit subkey derived from the Rijndael Key Schedule.
Step 6
Decryption Inversion & PKCS#7 Unpadding

During decryption with openssl enc -d, the exact reverse transformations are executed: InvShiftRows, InvSubBytes, AddRoundKey, and InvMixColumns. The output block is then XORed with the previous ciphertext block to recover $P_i$, and the trailing PKCS#7 padding bytes are safely stripped.

Step 7
Binary Comparison (`fc /b message.txt decrypted.txt`)

Executes a bit-for-bit binary comparison. Returns FC: no differences encountered, mathematically proving that the decrypted plaintext matches the original file identically.

🔬 RSA-2048 Internal Cryptographic Breakdown:

Step 1
Probabilistic Prime Generation ($p$ & $q$) via Miller-Rabin

OpenSSL executes repeated iterations of the Miller-Rabin primality test and Lucas tests to generate two distinct, cryptographically strong 1024-bit prime numbers $p$ and $q$.

Primes: p, q ∈ ℙ with |p| = |q| = 1024 bits
Step 2
RSA Modulus ($N$) and Euler's Totient ($\phi(N)$)

Multiplies the two primes to obtain the 2048-bit composite modulus $N = p \times q$. The security of RSA relies on the computational impossibility of factoring $N$ back into $p$ and $q$. It then computes Euler's Totient function $\phi(N) = (p-1)(q-1)$ or Carmichael's totient $\lambda(N) = \text{lcm}(p-1, q-1)$.

Modulus: N = p × q (2048 bits / 256 bytes) | φ(N) = (p - 1)(q - 1)
Step 3
Public Exponent ($e$) & Extended Euclidean Inversion ($d$)

OpenSSL chooses the Fermat prime $F_4 = 65537 = 2^{16} + 1$ as the public exponent $e$ (because its binary representation 10000000000000001 requires only 17 squaring and 1 multiplication operations). It then calculates the private exponent $d$ using the Extended Euclidean Algorithm such that $e \cdot d \equiv 1 \pmod{\phi(N)}$.

Public Exponent: e = 65537 | Private Exponent: d ≡ e⁻¹ (mod φ(N))
Step 4
Public Key Export (`public.pem`)

OpenSSL extracts only the public parameters $(e, N)$ and formats them into an ASN.1 DER sequence encoded in base64 (SubjectPublicKeyInfo). The private parameters ($p, q, d, d_p, d_q, q_{inv}$) remain strictly isolated in private.pem.

Step 5
OAEP Padding with SHA-256 (Optimal Asymmetric Encryption Padding)

Raw RSA ($c = m^e \pmod N$) is deterministic and vulnerable to mathematical chosen-ciphertext attacks. OAEP adds a random seed and runs Mask Generation Function 1 (MGF1) using SHA-256 to convert plaintext into an all-or-nothing randomized 256-byte block $M$.

Max Payload: 256 bytes - 2×(32 bytes SHA256) - 2 = 190 bytes maximum plaintext
Step 6
Encryption via Modular Exponentiation ($C \equiv M^e \pmod N$)

The sender encrypts the 256-byte padded block $M$ by raising it to the power $e$ modulo $N$. The resulting ciphertext $C$ is exactly 256 bytes (2048 bits) long and saved to encrypted.bin.

Step 7
Decryption via Chinese Remainder Theorem & Verification

The private key holder computes $M \equiv C^d \pmod N$ (accelerated 4x using CRT parameters). The receiver validates OAEP padding, unmasks the random seed, extracts plaintext, and confirms bit-for-bit equality via fc /b.

🔬 SHA-256 Internal Cryptographic Breakdown:

Step 1
Message Pre-Processing & 512-Bit Block Padding

SHA-256 processes messages in 512-bit (64-byte) blocks. The input data of length $L$ bits is padded by appending a single '1' bit, followed by $k$ zero bits such that the length is $\equiv 448 \pmod{512}$. Finally, the original length $L$ is appended as a 64-bit big-endian integer, ensuring total length is an exact multiple of 512 bits.

Padding: [Data] + [1] + [0...0] + [64-bit Length L] ≡ 0 (mod 512)
Step 2
Initialization of the 8 Working Registers ($H_0 \dots H_7$)

Before processing the blocks, eight 32-bit internal hash registers $(a, b, c, d, e, f, g, h)$ are initialized with the first 32 bits of the fractional parts of the square roots of the first 8 prime numbers (2, 3, 5, 7, 11, 13, 17, 19):

H_0 = 0x6a09e667, H_1 = 0xbb67ae85, H_2 = 0x3c6ef372, H_3 = 0xa54ff53a
H_4 = 0x510e527f, H_5 = 0x9b05688c, H_6 = 0x1f83d9ab, H_7 = 0x5be0cd19
Step 3
Message Schedule Expansion (16 Words Expanded to 64 Words)

Each 512-bit chunk is parsed into sixteen 32-bit words ($W_0 \dots W_{15}$). The algorithm then expands these 16 words into a full 64-word schedule ($W_{16} \dots W_{63}$) using bitwise rotation ($\text{ROTR}$), logical shifts ($\text{SHR}$), and modulo $2^{32}$ addition:

W_t = σ_1(W_{t-2}) + W_{t-7} + σ_0(W_{t-15}) + W_{t-16}
σ_0(x) = ROTR⁷(x) ⊕ ROTR¹⁸(x) ⊕ SHR³(x)
σ_1(x) = ROTR¹⁷(x) ⊕ ROTR¹⁹(x) ⊕ SHR¹⁰(x)
Step 4
The 64 Compression Rounds with Constants ($K_0 \dots K_{63}$)

SHA-256 executes exactly 64 compression rounds using 64 cube-root prime constants $K_t$. Each round transforms the 8 working variables using non-linear boolean operations:

  • Ch(e, f, g): Choose function = $(e \wedge f) \oplus (\neg e \wedge g)$.
  • Maj(a, b, c): Majority function = $(a \wedge b) \oplus (a \wedge c) \oplus (b \wedge c)$.
  • Σ_0(a) & Σ_1(e): $\text{ROTR}^2(a) \oplus \text{ROTR}^{13}(a) \oplus \text{ROTR}^{22}(a)$ and $\text{ROTR}^6(e) \oplus \text{ROTR}^{11}(e) \oplus \text{ROTR}^{25}(e)$.
  • Temporary Variables: $T_1 = h + \Sigma_1(e) + \text{Ch}(e, f, g) + K_t + W_t$ and $T_2 = \Sigma_0(a) + \text{Maj}(a, b, c)$.
  • Register Shift: $h \leftarrow g, g \leftarrow f, f \leftarrow e, e \leftarrow d + T_1, d \leftarrow c, c \leftarrow b, b \leftarrow a, a \leftarrow T_1 + T_2$.
Step 5
Intermediate Hash Addition & 256-Bit Digest Output

After all 64 rounds finish for a block, the working variables are added back into the hash state ($H_0 = H_0 + a, \dots, H_7 = H_7 + h$). After all 512-bit blocks are consumed, $H_0 \dots H_7$ are concatenated into the final 256-bit (32 bytes / 64 hex characters) output digest.

Step 6
Data Tampering & The Avalanche Effect (Proven with `fc /b`)

When even a single character (or 1 bit) is appended or modified in original.txt, the bitwise diffusion across the 64 compression rounds causes $>50\%$ of all bits in the final 256-bit digest to flip completely. Binary comparison with fc /b original_hash.txt modified_hash.txt confirms total divergence, mathematically guaranteeing instant tampering detection.
